# Agents guidelines

## General

- Always use simple and concise language, either to communicate with me or when writing things down. The main goal is that we communicate in a way that should be easily understood by everyone. Follow the guidelines from ISO 24495-1 for plain language.

## Elixir

- If you are working on an Elixir project, use `mise` to activate the required versions of Elixir and Erlang.
- If you are working on an Elixir project, before you commit something, always run `mix format` to guarantee that the code is correctly formatted.
- If you are working on an Elixir project, before you commit something, always run `mix credo` to guarantee that we are not introducing any new issues on the static analysis.
- If you are working on an Elixir project, always make sure that changes did not broke any test, run `mix test` as needed.

## Git

- When opening a pull request, creating a new Git branch or writing a Git commit message, we should always follow conventional commits specification (`feat`, `fix`, `docs`, `chore`, ...). If available, we need to include the Linear issue ID. For example, "feat(ARQ-421): Some short description of the commit/pull request.".
- When making Git commits, prefer to split into multiple meaningful commits that tell a story instead of a single giant commit. Don't keep amending the same commit and force pushing to remote. Only amend commits if you have a good reason for it.
- When creating a new Git worktree, place it on the `~/Developer/.worktrees` directory.
- When writing a pull request description, always include in the top a section with a "TLDR" section with a brief explanation of the changes in the PR (kind of like a "explain to me as if I was a five year old").
- When writing a pull request description, always include a section (after the "TLDR") with a brief explanation of the most relevant parts of the PR that needs a review with more attention or are more critical.
- When writing a pull request description, use the `show-me` skill for the description.

## Observability

- Observability should not be an after-thought when doing something, it should be part of the normal development work.
- We should have enough logging to help us debug problems, specially in production. At the very least, but not limited to, we should log error cases and possible warnings.
- We should instrument code for tracing. Traces allow us to pinpoint and measure specific parts of the system when investigating errors or performance issues.

## Linear

- When I say that we are starting to work on a Linear issue, assign it to me and move it to "In Progress".
- When creating new issues, use the `show-me` skill for the issue description.

## GitHub

- When creating or editing GitHub PR descriptions with `gh`, do **not** pass multi-line Markdown directly through `--body "..."` with escaped `\n`. Always write the PR body to a temporary Markdown file first, then use `--body-file`.
- PR body should not have new lines mid-sentence.
- When reviewing comments on a pull request, answer each comment individually. These comments should always indicate clearly that that comment was generated by AI (use the following format: `🤖 _Reply generated by AI_`). Leave a global comment on the pull request only if it makes sense or if replying to another global comment.
